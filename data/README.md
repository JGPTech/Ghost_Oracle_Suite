# `data/` — Sample bases

Per-tile shot data from the seven-qubit Hadamard-test circuit, in a single canonical `.npz` format. The directory ships with at least one QPU base and one noiseless GPU base so the headline benchmark and every probe runs out of the box without needing IBM Runtime credentials or a CUDA-capable GPU at first launch.

```bash
# From the repo root
python -m ghost_oracle.projection_benchmark
```

That command auto-finds whatever `job_*.npz` and `ghost_oracle_gpu_*.npz` (or `noiseless_base_*.npz`) it sees in this directory and runs against them.

---

## File naming

Three filename patterns appear here, with three different producers:

| Pattern | Producer | What it is |
|---|---|---|
| `job_<JOB_ID>.npz` | `ghost_oracle/dump.py` | Physical QPU shots, pulled from a completed IBM Runtime job |
| `ghost_oracle_gpu_<shots>shots_seed<seed>.npz` | `ghost_oracle/gpu.py` | Noiseless reference, generated by the GHZ closed-form sampler in `ghost_kernel.cu` Section 5 |
| `noiseless_base_<shots>shots_seed<seed>.npz` | `probes/probe4_build_base.py` | Same noiseless reference, generated by the readable Python statevector prototype |

The `auto_find_base(kind)` helper that every script uses resolves these as follows:

- `kind == "qpu"` matches `job_*.npz`.
- `kind == "gpu"` matches both `noiseless_base_*.npz` and `ghost_oracle_gpu_*.npz`, in that order.

Probes that need both kinds (Probe 6, 7, 8, 9, 9.1) auto-find one of each.

---

## File schema

Every base in this directory follows the same schema, regardless of producer. This is what makes physical QPU shots and GPU-generated noiseless shots drop-in interchangeable across every consumer.

| Key | Type | Shape | Description |
|---|---|---|---|
| `job_id` | `str` | — | Free-form label. `<IBM job ID>` for QPU dumps, `ghost_oracle_gpu_seed<seed>` for GPU samples, `noiseless_base_seed<seed>` for the Probe 4 prototype |
| `num_tiles` | `int` | — | Number of tiles in this base. Either 12 (historical runs, 3×4 sub-grid) or 16 (current 4×4) |
| `ctrl_tile{t}` | `uint8` | `(n_shots,)` | Per-shot control-qubit measurement for tile `t`, one of `{0, 1}`. `t` ranges from `0` to `num_tiles - 1` |
| `ghost_tile{t}` | `uint8` | `(n_shots, 4)` | Per-shot ancilla measurements for tile `t`, columns `[a1, a2, b1, b2]`, each one of `{0, 1}` |

GPU bases also include three diagnostic keys that QPU bases don't (and which the projection benchmark ignores):

| Key | Type | Description |
|---|---|---|
| `max_p0_residual` | `float` | Largest per-tile gap between empirical `P(ctrl=0)` and the analytical T3 prediction; should be at shot-noise scale |
| `max_anti` | `float` | Largest empirical `P(a1 ≠ a2)` or `P(b1 ≠ b2)`; should be exactly zero in the noiseless limit |
| `seed` | `int` | cuRAND seed used to generate the sample |

Both are loaded the same way:

```python
import numpy as np
d = np.load("data/ghost_oracle_gpu_4096shots_seed1340774840227267714.npz")
num_tiles = int(d["num_tiles"])
ctrl_dict  = {t: d[f"ctrl_tile{t}"]  for t in range(num_tiles)}
ghost_dict = {t: d[f"ghost_tile{t}"] for t in range(num_tiles)}
```

## Tile ↔ matrix-entry mapping

The 16-tile base covers a 4×4 matrix in row-major order: tile `t` corresponds to matrix entry `(r, c) = (t // 4, t % 4)`. The 12-tile base covers the first 12 entries of the same row-major order, leaving the last row partially empty — a historical artifact from when 4×4 clusters weren't reliable on the available IBM hardware.

Per-tile angles `(a, b)` are derived from a fixed matrix family `MATRIX_A`, `MATRIX_B` and the `data_to_angles` scaling:

```python
MATRIX_A = np.array([0.25, 0.50, 0.75, 1.00])
MATRIX_B = np.array([1.00, 0.80, 0.40, 0.10])

def data_to_angles(data, scale=ANGLE_SCALE):    # ANGLE_SCALE = 1.05
    return (data / np.max(np.abs(data))) * (np.pi / 2) * scale
```

Tile `t = (r, c)` was sampled at `(angles_a[r], angles_b[c])`. The `--matrix-a` and `--matrix-b` flags on `qpu.py` and `gpu.py` allow custom families, but every base shipped here uses the default above. See `docs/math.md` for what these angle ranges buy.

## What the noiseless and QPU bases differ on

By construction, both base types share the schema. They differ on three measurable axes, in increasing order of usefulness as a hardware-fidelity diagnostic:

**Ghost anti-correlation.** In the noiseless GHZ limit, `a1 = a2` and `b1 = b2` *deterministically* (see `docs/math.md`, "Deriving $T_3$"). Noiseless GPU bases satisfy this exactly: `P(a1 ≠ a2) = P(b1 ≠ b2) = 0` to machine precision. Physical QPU bases see decoherence in the GHZ block: `P(a1 ≠ a2) ≈ 0.15` and `P(b1 ≠ b2) ≈ 0.17` on the representative job shipped here, well below the independence null of 0.30–0.36. Probe 7 measures this directly.

**`P(ctrl=0)` residual against T3.** Both base types target

$$P(\text{ctrl}=0) = \tfrac{3}{4} + \tfrac{1}{4}\cos a \cos b$$

The noiseless base hits it to shot noise (~`1/√4096 = 0.016` per tile). The QPU base sits about `~0.10` MAE off it on the representative job. Probes 5 and 6 measure this; Probe 8 spends four phases trying (and largely failing) to attribute it to canonical channels.

**Agreement metric in production.** The tied-channel kernel computes `mean |projection − geometry|` per row at scale; running `projection_benchmark.py` shows this in the correctness check and per-shape output. GPU agreement lands around 0.01–0.06 (shot noise), QPU agreement around 0.10–0.20 (shot noise + hardware residual). This is the **certificate** the production architecture is built around — see `docs/architecture.md`, "The two channels."

If you point the benchmark at the same QPU job that fed Probes 7 and 8, you should reproduce the numbers above. Different jobs give different specific values inside the same range.

## Generating your own bases

For a noiseless reference (fast, no hardware needed):

```bash
python -m ghost_oracle.gpu                              # 4096 shots, random seed
python -m ghost_oracle.gpu --shots 8192 --seed 42       # reproducible
python -m ghost_oracle.gpu --verify                     # prints the per-tile sanity table
```

Output: `data/ghost_oracle_gpu_<shots>shots_seed<seed>.npz`.

For a physical QPU base (needs IBM Runtime credentials):

```bash
python -m ghost_oracle.qpu                  # submits the job, prints the JOB_ID, exits
python -m ghost_oracle.dump <JOB_ID>        # once the job completes, pulls it to .npz
```

Output: `data/job_<JOB_ID>.npz`.

The two scripts are deliberately separate so that `qpu.py` can submit and exit without holding a long-lived connection while the job queues, and `dump.py` can run later (potentially much later) once the job completes. The `.npz` is self-contained — re-analyzing it doesn't require IBM Runtime credentials, and there's no separate metadata file to keep in sync.

For the Probe 4 readable prototype (slow Python statevector simulator, used for tracing the math):

```bash
python probes/probe4_build_base.py --shots 4096
```

Output: `data/noiseless_base_<shots>shots_seed<seed>.npz`. Byte-compatible with `gpu.py`'s output; `gpu.py` should be preferred for any actual base generation since it's roughly 1000× faster.

## Reproducibility

GPU bases are seedable and reproducible. Passing the same `--seed` to `gpu.py` produces a byte-identical `.npz` (subject to cuRAND determinism guarantees on a given GPU model — Philox 4×32×10, which is reproducible across CUDA versions but not necessarily across vendor GPUs).

QPU bases are not bit-reproducible. Even at the same `--shots` and `--num-tiles` against the same IBM backend, two consecutive submissions give different bit sequences because the hardware is a physical random process. They are *statistically* reproducible — distributional metrics like `P(ctrl=0)` per tile and Probe 7's anti-correlation hold within shot noise across re-runs.

Every probe acknowledges this in its `HISTORICAL CONTEXT:` block: "Running this script against the sample bases shipped in `data/` will produce different specific numbers, but the qualitative finding holds."

## File sizes

A typical 16-tile base at 4096 shots/tile:

- Raw `(uint8)` payload: `16 × 4096 × 5 bytes = 320 KB` (ctrl + 4 ghost columns per shot)
- Compressed `.npz` on disk: typically 40–80 KB (random bitstrings compress only modestly)

Bases for larger sweeps or smaller matrix sizes scale linearly with `num_tiles × shots`.

## What's *not* in here

A few things you might expect that aren't:

- **No raw IBM Runtime artifacts.** `dump.py` extracts what the suite needs and discards the rest. If you want the full Runtime result, fetch it separately from IBM with the same `job_id`.
- **No analysis outputs.** Probe stdout, benchmark tables, and plots are produced on the fly and not persisted here. Capture them with shell redirection if you want them.
- **No pre-bucketed counts.** The projection-channel kernel does the `(ctrl, ghost4) → 18-int histogram` collapse at load time in roughly O(n_shots). Storing pre-bucketed counts would save a few hundred milliseconds per benchmark run at the cost of complicating the schema; the current design favors one canonical layout over slightly faster cold starts.
